2. BROWSER VIEW / WEBVIEW WRAPPER ARCHITECTURE
================================================================================

--- PROTON MAIL COMPANION ---

The Proton project uses a FULL Electron BrowserWindow (not BrowserView) for each
Proton Mail account. Each account gets its own partition:

  const partition = `persist:proton-companion-account-${accountId}`;

The BrowserWindow is created with:
  - nodeIntegration: false
  - contextIsolation: true
  - partition for isolated cookies/session
  - Custom user agent to look like a regular Chrome browser
  - Custom preload script that exposes `window.protonCompanion` API

The preload script (src/preload/index.ts) exposes a rich API:
  window.protonCompanion = {
    app: { show, hide, quit, openExternal, handleMailto, showNotification, ... }
    notification: { getCurrent, act, dismiss }
    settings: { get, set }
    accounts: { list, add, switch, rename, remove, reconnect }
    runtime: { get, openPanel }
    workspace: { getState, setMailbox, refresh, syncProtonMailbox, ... }
    gmail: { listThreads, getThread, ... }
    onSettingsChanged, onAccountsChanged, onRuntimeChanged, ...
  }

The Proton project also uses injected scripts (NOT preload) for:
  - shellUi.ts: Account switcher, settings drawer, toast notifications
  - shellUiNotificationShim.ts: Notification API override
  - protonMailboxObserver.ts: DOM scraping for mailbox items

--- MAILBRIDGE ---

MailBridge uses Electron BrowserView (deprecated but still functional):

  const view = new BrowserView({
    webPreferences: {
      partition: `persist:proton-${accountId}`,
      nodeIntegration: false,
      contextIsolation: true,
      sandbox: true
    }
  })

The BrowserView is set on the main window via:
  mainWindow.setBrowserView(view)
  view.setBounds({ x: 0, y: 0, width: 800, height: 600 })

Scripts are injected via executeJavaScript() - NOT preload:
  - injectNotificationInterceptor(view)  - Notification API override
  - injectMailboxObserver(view)          - DOM scraping

The notification popup uses a SEPARATE BrowserWindow with:
  - A generated preload script that exposes window.notificationOverlay
  - data:text/html URL with inline HTML/CSS/JS

3. NOTIFICATION INTERCEPTION SYSTEM (Proton Mail Companion)
================================================================================

The Proton Mail Companion uses a 3-layer notification interception strategy:

--- LAYER 1: NOTIFICATION API MONKEY-PATCH (Primary) ---

File: src/main/shellUiNotificationShim.ts

This is the MOST RELIABLE method. It replaces the browser's Notification API:

  window.Notification = class CompanionNotification extends EventTarget {
    constructor(title, options = {}) {
      super();
      this.title = String(title ?? appName);
      this.body = typeof options.body === 'string' ? options.body : '';
      this.silent = options.silent === true;
      this.tag = typeof options.tag === 'string' ? options.tag : '';

      // Emit show event
      queueMicrotask(() => {
        const event = new Event('show');
        this.dispatchEvent(event);
        this.onshow?.call(this, event);
      });

      // Forward to main process
      void window.protonCompanion.app.showNotification({
        provider: 'proton',
        sender: this.title,
        subject: this.title,
        snippet: this.body,
        title: this.title,
        body: this.body,
        silent: this.silent,
        notificationKey: this.tag || [this.title, this.body].filter(Boolean).join(':'),
      });
    }
  }

Key features:
  - Captures Proton's native Notification calls
  - Extracts sender (title), subject, snippet (body)
  - Forwards to main process via protonCompanion.app.showNotification()
  - Respects notification enable/disable settings
  - Falls back to MutedNotification when disabled

--- LAYER 2: DOM SCRAPING (Mailbox Observer) ---

File: src/main/protonMailboxObserver.ts

A MutationObserver-based system that scrapes the Proton Mail DOM:

  new MutationObserver(() => scheduleSync()).observe(document.documentElement, {
    childList: true,
    subtree: true,
    characterData: true,
    attributes: true,
  });

Features:
  - Collects all visible mailbox rows
  - Extracts sender, subject, snippet, date, unread status
  - Validates rows against exclusion criteria
  - Deduplicates by spatial coordinates
  - Stores items in window.__protonCompanionMailboxItems
  - Calls window.protonCompanion.workspace.syncProtonMailbox(items)
  - Periodic sync every 10 seconds
  - Debounced mutation sync (120ms delay)

--- LAYER 3: PRELOAD SCRIPT UNREAD MONITORING ---

File: src/main/protonMailboxObserver.ts (also)

The preload script monitors unread counts by:
  1. Parsing document.title for "(N) Inbox" pattern
  2. Scanning sidebar for unread badges
  3. Using MutationObserver on the title element
  4. Dispatching unread count changes via IPC

--- MAILBRIDGE APPROACH ---

MailBridge uses a similar but simpler approach:

  // Notification API monkey-patch
  injectNotificationInterceptor(view) -> patches window.Notification

  // Mailbox observer
  injectMailboxObserver(view) -> MutationObserver + DOM scraping

  // Unread monitoring
  view.webContents.on('page-title-updated', ...) -> parse title

The key difference: MailBridge stores data on window.__lastProtonNotification
and window.__mailbridgeLastMailboxItems, while the Proton project uses
window.protonCompanion.app.showNotification() via the preload bridge.

4. DOM SCRAPING / MAILBOX OBSERVER SYSTEM
================================================================================

--- PROTON MAIL COMPANION (protonMailboxObserver.ts) ---

This is the most sophisticated DOM scraping system. Key algorithms:

ROW DETECTION (Two-pass):
  Pass 1: Explicit selectors
    [data-proton-companion-thread]
    [data-proton-thread]
    [data-testid*="message-row"]
    [data-testid*="conversation-row"]
    [data-testid*="thread-row"]
    [class*="conversation-row"]
    [class*="message-row"]
    [role="row"]
    [role="listitem"][aria-selected]

  Pass 2: Generic fallback (if no explicit rows found)
    main [role="row"]
    main [role="listitem"]
    main a[href]
    main button

ROW VALIDATION (isLikelyMailboxRow):
  - Must be visible (offsetParent !== null)
  - Width >= 220px, Height >= 28px and <= 240px
  - Must not be in excluded regions (aside, nav, header, footer, form, dialog)
  - Must not contain textarea or contenteditable
  - Must have >= 2 meaningful text blocks
  - OR match known row selectors
  - OR have an href containing /mail, /inbox, message

ROW EXTRACTION (toSummary):
  Uses multi-strategy text extraction:

  1. Explicit attribute selectors:
     [data-proton-sender], [data-testid*="sender"], [class*="sender"], strong, b
     [data-proton-subject], [data-testid*="subject"], [class*="subject"]
     [data-proton-snippet], [data-testid*="snippet"], [class*="snippet"], [class*="preview"]
     time[datetime], [data-proton-date], [data-testid*="date"], [class*="date"], [class*="time"]

  2. Text block collection:
     - Collect direct children text
     - If only 1 child, go one level deeper
     - Fall back to tree walker

  3. Filtering:
     - isLikelyDateText: time patterns, "today", "yesterday"
     - isLikelyMailboxIdentityText: email addresses, "mail.proton.me"
     - isLikelyMailboxMetadataBlock: "Unread", "Official", "Important", etc.

  4. Sender resolution:
     - If no sender from attributes, use first meaningful block
     - If sender == subject, use alternative block

  5. Subject resolution:
     - Skip identity text, dates, metadata
     - Prefer blocks >= 3 chars

  6. Snippet resolution:
     - Remaining blocks after sender/subject
     - Skip identity text
     - Max 220 chars

UNREAD DETECTION (inferUnread):
  - Check aria-label for "unread"
  - Check font-weight >= 600 on child elements

DEDUPLICATION (dedupeRows):
  - Sort by top, then left position
  - Filter out rows contained within other rows

--- MAILBRIDGE (proton-handler.ts injectMailboxObserver) ---

Simplified version with similar structure:
  Pass 1: Explicit selectors (data-proton-thread, data-testid*, role="row")
  Pass 2: Generic fallback (div[class*="items"] > div, main > div > div)

Key differences from Proton:
  - Uses getMeaningfulTextBlocks() instead of collectTextBlocks()
  - Less sophisticated filtering
  - Stores on window.__mailbridgeLastMailboxItems

5. NOTIFICATION BUILDING & ENRICHMENT
================================================================================

--- PROTON MAIL COMPANION ---

The Proton project builds notifications through a multi-step pipeline:

STEP 1: Source Detection (in main process)
  The title change event fires -> parseUnreadCount(title) -> detect increase
  OR the Notification API monkey-patch fires -> capture sender/subject/body

STEP 2: Notification Enrichment (notificationParsing.ts)
  Functions:
    sanitizeNotificationText(value) - Remove control chars, normalize whitespace
    normalizeNotificationValue(value) - Sanitize + null check
    isGenericProtonNotificationText(value) - "new email received", "new message"
    isPlaceholderProtonNotificationText(value) - empty, "unknown sender", etc.
    isSeparatorOnlyNotificationLine(value) - decorative separators
    parseProtonNotificationBody(value) - Parse "From: X\nSubject: Y\nBody" format
    isLikelyProtonMailboxIdentityText(value, account) - Account email/name
    isLikelyInvalidProtonMailboxItem(account, item) - Filter junk
    selectLatestProtonMailboxItem(items) - Sort by date, prefer unread

STEP 3: Notification Request (from preload or injected script)
  {
    provider: 'proton',
    accountId: string,
    notificationKey: string (for dedup),
    sender: string,
    subject: string,
    snippet: string,
    silent: boolean,
    actions: [{ id: 'open', title: 'Open' }]
  }

STEP 4: Notification Object (UnifiedNotification)
  {
    provider: 'proton' | 'gmail' | 'app',
    accountId: string | null,
    notificationKey: string,
    threadId: string | null,
    messageId: string | null,
    sender: string,
    subject: string,
    snippet: string,
    silent: boolean,
    actions: Array<{ id: string; title: string }>
  }

--- MAILBRIDGE ---

Simpler pipeline:

STEP 1: Title change -> parseUnreadCount -> detect increase
  OR Notification API intercept -> capture data

STEP 2: Build notification object (NewEmailNotification)
  {
    id: `proton-${accountId}-${currentCount}-${Date.now()}`,
    accountId,
    provider: 'proton',
    notificationKey: buildNotificationKey(...),
    from: { name, address },
    subject,
    snippet,
    timestamp: Date.now()
  }

STEP 3: Enrichment in NotificationService
  buildDisplaySubject() - Filter generic subjects
  buildDisplaySnippet() - Build "From: X\nSubject: Y\nBody" format
  normalizeNotificationText() - Clean text

6. DEDUPLICATION & QUEUING SYSTEM
================================================================================

--- PROTON MAIL COMPANION (notificationCenter.ts) ---

  class NotificationCenter {
    flushDebounceMs: 1800 (1.8 seconds)
    dedupeWindowMs: 90000 (90 seconds)

    enqueue(item):
      dedupeKey = `${provider}:${accountId}:${notificationKey}`
      if (now - lastSeen < dedupeWindowMs) return  // Skip duplicate
      seen.set(dedupeKey, now)
      pruneSeen(now)  // Clean old entries

      queueKey = `${provider}:${accountId}`
      queue.items.push(item)
      if (!queue.timer) {
        queue.timer = setTimeout(() => flush(queueKey), flushDebounceMs)
      }

    flushAll():
      for each queue: flush(queueKey)

    flush(queueKey):
      clearTimeout(queue.timer)
      delete queue
      if (items.length > 0) onFlush(items)
  }

Key behaviors:
  - Debounces: Multiple notifications within 1.8s are batched
  - Deduplicates: Same notification key ignored for 90 seconds
  - Per-account queuing: Notifications from different accounts are separate
  - Auto-prune: Old seen entries cleaned on each enqueue

--- MAILBRIDGE (notification-center.ts) ---

  class NotificationCenter {
    flushDebounceMs: 250 (250ms - much faster)
    dedupeWindowMs: 5000 (5 seconds - much shorter)

    Same structure as Proton but with tighter timing.
  }

Key differences:
  - MailBridge flushes 7x faster (250ms vs 1800ms)
  - MailBridge dedup window is 18x shorter (5s vs 90s)
  - This means MailBridge may show more duplicate notifications

--- PROTON MAIL COMPANION ---

  async function playNotificationSound(soundUrl: string) {
    if (!soundUrl) return;
    if (activeNotificationAudio) {
      activeNotificationAudio.pause();
      activeNotificationAudio.currentTime = 0;
    }
    const audio = new Audio(soundUrl);
    audio.preload = 'auto';
    audio.volume = 1;
    activeNotificationAudio = audio;
    await audio.play();

Sound is loaded from the settings and passed to the popup.

10. UNREAD COUNT MONITORING
================================================================================

--- PROTON MAIL COMPANION ---

Two methods:

Method 1: Title parsing (preload/index.ts)
  function inferUnreadCount() {
    const titleCount = parseUnreadCount(document.title);
    if (titleCount > 0) return titleCount;
    // Fallback: scan sidebar for badges
    const candidates = collectUnreadCandidates();
    let highest = 0;
    for (const candidate of candidates) {
      highest = Math.max(highest, parseBadgeCount(candidate.textContent));
    }
    return highest;
  }

Method 2: Mailbox observer (protonMailboxObserver.ts)
  - Counts unread items from DOM scraping
  - Reports via window.protonCompanion.workspace.syncProtonMailbox()

--- MAILBRIDGE ---

Method 1: Title parsing (proton-handler.ts)
  view.webContents.on('page-title-updated', (_e, title) => {
    const currentCount = parseUnreadCount(title);
    const prevCount = lastUnreadCounts.get(accountId) ?? -1;
    if (prevCount >= 0 && currentCount > prevCount) {
      // New email detected!
      notifyForProtonMail(view, accountId, currentCount, increasedBy);
    }
    lastUnreadCounts.set(accountId, currentCount);
  });

Method 2: Mailbox observer (injected script)
  - Stores on window.__mailbridgeLastMailboxUnread
  - Can be read by main process

     - Proton falls back to generic selectors when no explicit rows found

  ❌ Sender/subject resolution heuristics
     - Proton has sophisticated fallback: explicit attrs -> text blocks -> metadata filtering
     - MailBridge is simpler

  ❌ Unread inference from font-weight
     - Proton checks computed font-weight >= 600
     - MailBridge only checks aria-label

  ❌ Logo/icon resolution for notifications
     - Proton resolves sender logos via BIMI/favicon
     - MailBridge shows letter glyph only

  ❌ Gmail integration (not applicable, but shows architecture)

  ❌ Workspace-level mailbox rendering
     - Proton has a full unified workspace
     - MailBridge only has BrowserView per account

  ❌ Notification grouping with previews
     - Proton supports grouped notifications with preview list
     - MailBridge shows individual notifications

  ❌ Settings sync via preload bridge
     - Proton uses protonCompanion.settings.get()
     - MailBridge reads directly from storage

  ❌ Custom theme support in notifications
     - Proton supports 7 themes with CSS variables
     - MailBridge has fixed dark theme

  ❌ Accessibility improvements
     - Proton uses aria-hidden, semantic HTML
     - MailBridge is similar but less thorough

13. KEY DIFFERENCES & FEATURES TO ADOPT
================================================================================

--- TIMING CONSTANTS ---

  Proton:
    flushDebounceMs: 1800 (1.8s)
    dedupeWindowMs: 90000 (90s)
    NOTIFICATION_POPUP_AUTO_CLOSE_MS: 16000 (16s)
    MUTATION_SYNC_DELAY_MS: 120 (120ms)
    PERIODIC_SYNC_INTERVAL_MS: 10000 (10s)
    MAILBOX_RENDER_ACK_TIMEOUT_MS: 1200

  MailBridge:
    flushDebounceMs: 250 (250ms)
    dedupeWindowMs: 5000 (5s)
    autoDismissDuration: 5000-16000 (configurable)
    MUTATION_SYNC_DELAY_MS: 120 (120ms)
    MAILBOX_SYNC_INTERVAL_MS: 10000 (10s)
    NOTIF_COOLDOWN_MS: 3000 (3s)

--- RECOMMENDATION: ADOPT PROTON'S TIMING ---

  MailBridge's 250ms flush is too aggressive - may cause jitter.
  MailBridge's 5s dedup is too short - may show duplicates.

  Recommended:
    flushDebounceMs: 1000 (1s) - compromise between 250ms and 1800ms
    dedupeWindowMs: 30000 (30s) - compromise between 5s and 90s
